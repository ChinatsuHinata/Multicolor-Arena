## 必须保持的外部契约

1. 保持卡牌 ID、JSON 字段、能力绑定 ID、既有构筑资格和卡组文件格式。修改机制时才更改卡牌行为，并逐张记录规则依据。
2. 保持引擎对界面和联机开放的命令名称、参数、错误结果及提交时机；界面的选择仍只暂存，确认时统一校验并提交。
3. 保持实例 ID、区域版本、堆叠顺序、触发顺序、随机数状态和隐藏信息投影。重整期间先保留引擎状态字段形状；需要改字段时单独做版本迁移。
4. 保持旧卡组可读、当前对局可操作、悔棋/重连可恢复。回放格式或规则指纹变化要显式处理，不以“能启动游戏”代替兼容检查。

## 实施顺序

### 0. 固定当前行为基线

- 在独立工作目录中保存当前工作区的可恢复快照；记录 Godot 版本、卡牌清单、规则清单和测试命令。不要直接从 `main` 的旧提交建工作树后误以为包含当前未提交改动。
- 为测试配置隔离的卡组、设置、回放与联机数据目录。先跑现有规则、界面、自动整局和联网测试，记下原有失败与耗时；之后仅把新增失败视为本次重整回归。
- 建立自动生成的“卡牌 ID → 类别 → 能力绑定/效果键 → 主要入口 → 对应测试”矩阵。未覆盖项显式列出，避免把“数据库能加载”误称为“这张卡能玩”。

### 1. 先补保护网，不改规则实现

- 全库静态门槛：513 张注册卡都能加载；绑定的实现与效果键都已登记；缺图、无效参数、重复 ID 立即失败。
- 按能力类型做运行时抽样和逐卡入口检查：能否合法使用/启动、选择目标和付款、进入堆叠或触发队列、完成结算。对不能正常使用的禁构筑牌和衍生物检查其实际进入途径。
- 对高风险路径加入固定种子场景：付款取消不改状态、目标换区失效、触发排序、复制/替代/计时、同时伤害与死亡、单张牌多种能力，以及双方视角的隐藏信息。
- 保存关键动作的可比较结果：公开与私有状态投影、堆叠和待选择、实例及区域版本、随机数状态。日志文本或画面像素不作为规则等价的唯一依据。已有错误需先确认规则裁定，不能机械固化为正确结果。

### 2. 每次只重整一条边界

- 第一批选择不改变规则状态的展示或只读查询；保留原公开函数作转发入口。先验证调用方和界面，再进入有状态规则。
- 有状态能力按一个能力族或一小组卡迁移：先保留旧分发入口，在新模块中接同样的目标、支付、触发、结算契约；每批列出受影响的卡牌 ID。不要一次迁移整个卡池，也不要同时改 JSON 格式和规则流程。
- 对纯查询可让新旧实现接收同一状态并比较结果；对有副作用的效果，只在独立复制的对局上比较相同命令序列，不能在同一对局执行两遍。
- 每批迁移后删除该批旧分支和临时桥接，保持唯一生效路径；下一批才开始。核心 `duel_engine.gd` 可以先作为稳定门面，不急于替换所有状态字典。

### 3. 最后迁移状态所有权

- 支付、目标、区域移动、触发、战斗等共用状态变化应在对应能力族稳定后逐项抽离。每项先明确输入、输出、事件顺序和失败时状态是否保持不变。
- 状态字段重命名或改类型时，先给快照/存档定义明确版本及升级读取路径，再迁移引擎字段；验证悔棋、断线恢复、观战投影和旧文件读取。
- 联机两端必须使用一致规则指纹。变更影响旧回放时，明确拒绝原因或提供迁移；不要静默播放出不同结局。

## 每批变更的合入门槛与回退

一批变更只解决一个边界，并附上受影响卡牌 ID、原入口/新入口和风险。合入前必须满足：卡牌及卡图全量加载通过；相关规则和界面测试通过；既有完整回归没有新增失败；固定种子对局能完成；涉及状态时通过编码恢复、双席位投影和联机命令校验。记录失败差异并修复后再继续下一批。

如出现未解释的卡牌失效、结算顺序变化、旧卡组打不开或状态恢复不同，停止扩大迁移范围，回退本批改动。不要靠新增特例绕过回归门槛。一次只合入一小批，使回退不影响此前通过的批次。

## 首个可执行批次

1. 只新增卡牌覆盖矩阵与统一测试入口，不改任何卡牌效果或存档格式。
2. 在现有测试上补三类缺口：全库绑定可达性、代表性固定种子对局、状态快照往返。
3. 用测试结果挑选一个边界清楚的只读入口做第一次抽取；完成一次“旧入口转发 → 行为对比 → 全套回归 → 删除重复实现”的循环，再决定下一批。
