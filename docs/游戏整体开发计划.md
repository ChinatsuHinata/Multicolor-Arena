## 2. 推荐的语言方案及选择理由

### 2.1 把“编写规则”和“编写卡牌”分开

推荐使用 **GDScript 编写引擎、界面和可独立复用的能力模块；JSON 编写卡牌资料、构筑规则和能力绑定，可选用已有的声明式效果配置**。JSON是数据格式，不是另一门需要学习控制流程的编程语言。中文字段只是给卡牌作者使用的固定词汇，实际运行时会转换成引擎内部的类型化数据。

| 工作 | 推荐载体 | 人工修改方式 |
| --- | --- | --- |
| 回合、执行权、支付、战斗和胜负规则 | GDScript | 修改一个负责该规则的模块，附对应规则测试 |
| 卡名、称号、角色名、种族、颜色、费用、图像与能力文字 | JSON | 复制模板，填值或选择枚举项 |
| 伤害、抓牌、治疗、移动区域、指示物等常规效果 | JSON中的效果列表 | 选择已经实现的操作并填参数 |
| 复杂能力、规则例外与尚未有模板的机制 | 独立GDScript能力模块 | 可直接编写脚本，登记后由卡牌引用；成熟机制再抽成复用模块 |
| 日常批量录入和核对牌面 | 原始牌表及未来录入工具 | 可作为导入来源，但不直接执行自然语言效果 |
| 整体计划、裁定和编写说明 | Markdown | 直接修改文字，方便比较历次变化 |

现有游戏已经使用GDScript，继续使用可以保留组卡器、存档和3D桌面。核心规则改为明确类型的类与函数，避免继续用一个巨大字典和大量界面回调承担所有逻辑。Godot支持GDScript类型标注，也原生提供JSON解析与错误位置报告。[GDScript类型说明](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/static_typing.html)、[JSON解析说明](https://docs.godotengine.org/en/stable/classes/class_json.html)。

### 2.2 与其他方案的取舍

| 方案 | 阅读与编牌 | 后续维护代价 | 当前建议 |
| --- | --- | --- | --- |
| GDScript + 中文JSON | 常规卡按模板填写，特殊卡写小脚本；引擎与卡牌边界清楚 | 需要先建设效果库、校验器和编写手册 | **优先推荐** |
| 全部GDScript，每张卡一个脚本 | 能写注释和任意逻辑，但每张卡都需要理解程序接口 | 容易重复支付、目标、区域处理逻辑；需强制统一接口 | 若用户希望亲自写程序，可选 |
| C# + JSON | 卡牌作者的体验与第一项基本相同，核心更适合熟悉C#的人维护 | 现有规则代码需迁移，另需匹配Godot .NET开发环境 | 目前没有必要仅为编牌而切换 |
| GDScript + YAML | 配置可写注释，括号较少 | 增加解析器和格式约定，缩进错误更需照顾 | 若用户强烈偏好此语法，再评估 |

C#使用Godot的.NET开发路径，详见[官方C#说明](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)。这里对工作量的判断基于本项目当前以GDScript为主的实际情况，不表示其他语言不能制作这款游戏。

不建议为了新卡录入，先创造一门自由书写的中文编程语言。限定的中文操作名已足够表达大量常规卡；任意自然语言的含义并不稳定，不适合直接作为对战裁定。

### 2.3 这个方案的代价也应说明

JSON需要英文半角引号、逗号和括号，不能直接写行尾注释。可提供明确的“作者备注”字段。首期校验器应直接报出“哪张卡、哪个字段、哪里填写有误”，以后再加表单录入界面。

配置不是万能的：一张卡写了“造成伤害”，引擎必须已经有对应的伤害操作。一张卡发明了新的资源或改变执行权规则，就需要先开发该机制。脚本不能只在“结算时”运行：构筑、开局、合法性查询、替代效应、触发生成、持续属性和回合推进都需要正式扩展入口。不会出现“只写一句能力文字，游戏就自动正确理解”的承诺。

## 3. 人工编写一张新卡的完整过程

### 3.1 先看一张卡的完整样例

以下以牌表中的恋符「极限火花」说明拟议格式。它是**早期声明式方案样例，不是当前加载器直接接受的格式**。当前实际格式采用“能力绑定”，见 `cards/99.json` 和 `docs/卡牌数据库与编写说明.md`。卡牌颜色与费用分别保存，费用为0的某色仍可构成该卡的颜色。

```json
{
  "格式版本": 1,
  "卡牌ID": "soi_spell_102",
  "名称": "恋符「极限火花」",
  "称号": "",
  "角色名": "",
  "类别": "符卡",
  "子类别": ["角色"],
  "颜色": ["黄"],
  "费用": {"黄": 3},
  "图片": "res://recourse/demo素材/image99.png",
  "使用约束": [
    {"类型": "操控指定角色单位", "角色名": "雾雨魔理沙"}
  ],
  "能力文字": "该牌对目标造成5点伤害。",
  "能力": [
    {
      "类型": "基本",
      "目标": [
        {"键": "受击者", "对象": ["单位", "玩家"], "最少": 1, "最多": 1}
      ],
      "效果": [
        {"操作": "造成伤害", "目标引用": "受击者", "数值": 5}
      ]
    }
  ],
  "来源": {"工作表": "SPELL （符卡）", "编号": "SOI-102"},
  "作者备注": "数值与能力文字必须同步核对。"
}
```

这个例子的目标既可能是单位，也可能是玩家，依据完整规则1.123；不能把所有伤害符卡默认写成“伤害对手”。角色约束在使用时检查，不用在结算时重新检查操控对应角色的条件（1.154、1.156），但目标合法性仍要重新检查（7.1.5）。

卡牌ID不能只取牌面编号：现有牌表中不同种类存在重复的SOI编号。稳定ID应含系列和类别；同一张牌的异画使用同一个规则身份，再单独记录图像版本。套牌同名限制按完整名称归组，不按图片文件或稀有度区分。

### 3.2 从填写到实际使用

1. **选模板。**根据单位、符卡、道具、结界复制对应模板。设定新的稳定ID，不覆盖现有卡。
2. **填写牌面。**名称拆分为完整名、称号、角色名；填写颜色、费用、单位属性、种族及图像路径。玩家预览仍遵循当前要求，只额外显示完整卡名与能力文字，不重新堆出费用和攻防说明。
3. **声明能力。**区分主要能力和自机能力，再区分基本、触发、启动、静止、替代、规则类能力。填写生效区域、事件、条件、是否可选、目标、支付、效果及持续时间。
4. **校验配置。**检查字段、ID、图片、整数数值、合法枚举、目标引用、效果操作是否已实现。不认识的操作必须拒绝加载，并显示错误，不能静默当作无效果卡。
5. **编写最小案例。**检查一次正常使用，以及至少一个关键边界，例如目标消失、资源不足、反制或自机能力未开启。
6. **在测试对局验收。**核对卡图和文字，再核对实际事件记录。文字改了不等于效果改了；两者都需检查。
7. **加入可用卡池。**通过后才标为正式可用，记录卡池版本和开发日志。旧卡组按稳定ID迁移，不能因为更换图片而失效。

### 3.3 一次出牌在引擎里的实际旅程

以使用上面的符卡为例：

`拖动手牌 → 检查执行权与使用时机 → 检查角色约束 → 选择目标 → 选择支付 → 确认使用 → 进入对抗 → 双方响应/让过 → 结算 → 伤害及后续判定 → 符卡去墓地 → 继续问询执行权`

- 拖动只提出“我想使用这张牌”，不会直接扣血或把牌从手中删除。
- 引擎检查是否为自己主要阶段、非战斗中、对抗为空且有执行权；该牌没有高速属性。
- 确认操控雾雨魔理沙的单位，选择一个合法单位或玩家，支付3点黄色。每张颜色盘牌横置后只能支付自己某一种颜色的1点；合法的颜色值能力也可参与支付。
- 完整规则7.1要求宣言、模式、目标和支付处于同一次不可插入响应的使用过程。界面可先暂存选择、最后整体提交；内部必须保持规则顺序及费用导致的事件，失败或取消时完整恢复。
- 对手可在之后的问询窗口响应，例如使用反制。发动后的能力不会因来源离场自动消失；目标仍要在结算时复查。
- 顶端对象结算后重新开放问询，不能把整条对抗一次性结算掉。
- 效果通过统一的“造成伤害”操作执行，由规则模块处理防止、替代、伤害标记、生命变化、死亡及游戏结束；卡牌作者不用重复写这些基础规则。

**普通新卡为什么方便：**另一张常规伤害牌可复用“造成伤害”，改目标条件和数值即可。但若其使用条件、费用、时机或附加效果不同，也必须填写对应配置，不能只改能力文字。

**复杂新卡怎么办：**先判断是否能组合现有操作；不能时新增一个专门的GDScript处理器。处理器通过统一接口请求选择和产生事件，不直接操作界面、场景节点或存档。JSON只引用已登记的处理器ID；未来联网不会执行对手任意提供的脚本。

## 4. 现有成果与正式对战之间的差距

已具备：主菜单、组卡、保存/重命名/复制粘贴、主副卡与自机槽、完整卡名、多色筛选、拖放增减、双方选牌、投点、3D战场与牌堆厚度、投降返回。

v0.5已替换旧演示逻辑：起手4张、六阶段、独立颜色支付、8张卡的实际效果、阻挡、执行权与堆叠均由独立引擎处理。原先起手5张、固定3点能量、符卡统一2点伤害、道具治疗的行为已从对战入口移除。不能将此进度理解为已实现全牌表。

迁移时保留已认可的界面布局、拖放习惯和存档。现有“卡组保存容量70主卡+10副卡+1自机”是产品编辑容量；正式对战合法性是另一套检查：50张主牌、同名上限、自机同名限制等。保存草稿不强制满足正式50张，不增加强制引导。

当前仅有8种演示卡。排除所选自机同名牌后，按通常每种4张计算，剩余7种至多28张，**不足以组成正常50张的合法套牌**。用户已选择先用这8张通过“不检查卡组”测试完整对局。正式构筑验收前需扩大测试卡池（至少13种可加入主牌的不同完整名称，另准备自机；特殊构筑规则另计）。资料中的全牌表不是“所有卡牌效果已实现”的证明。

本轮按照用户批准的8张测试范围，“不检查卡组”同时放宽50张、主牌同名4张和自机同名限制；仍检查自机存在、70/10容量、数据格式、已实现ID及常规构筑资格。仅用于测试，不等于这些重复卡组成为正式合法卡组。

## 5. 游戏的整体状态

以下是引擎设计状态，不是强制玩家按顺序浏览菜单。主菜单的入口自由使用，只有点击开始对战时才检查必需条件。

| 状态 | 玩家能做什么 | 离开条件 |
| --- | --- | --- |
| 主菜单 | 人机、联网、编辑牌组、设置 | 选择入口 |
| 编辑牌组 | 新建、拖放增减、保存、命名、复制粘贴、检索 | 返回或使用已保存卡组；未保存更改沿用确认处理 |
| 对局准备 | 双方选卡组、设定测试选项 | 开始时校验，错误仅在此时提示 |
| 先后手决定 | 投点赢家选择先手或后手 | 决定完成；平点重投；保留人机必定投1选项 |
| 对局初始化 | 创建双方实例、洗牌、20生命、放置自机 | 初始化完成 |
| 起手与调度 | 每人抓4张，选择一次换任意张或保留 | 双方完成；被换牌随机排序置底，再抓等量 |
| 回合进行 | 执行六阶段及其中的问询、战斗和选择 | 某方获胜/失败/投降 |
| 结算中 | 播放效果，必要时由指定玩家做选择 | 当前对象结算完成并处理后续判定 |
| 对局结束 | 展示结果与必要记录 | 回到进入对战前的对局准备页 |
| 联网等待/重连（后续） | 等待对方、恢复经裁定的状态 | 继续原逻辑状态或按断线规则结束 |

动画是显示状态，不应决定规则何时生效。人机思考、等待联网也不是新的回合阶段，它们只是等待某个玩家提交动作。

投降属于全局动作，任何阶段包括等待选择时都可提出。游戏结束后不再接受出牌、支付或继续结算命令。

## 6. 区域、对象与公开信息

完整规则4.01写“9个”，实际列出8个，4.1—4.8也展开8个。本计划暂按这8个建模，将数量笔误列入待确认。

| 区域 | 谁可见 | 核心约束与表现 |
| --- | --- | --- |
| 牌库 | 隐藏内容，仅公开数量 | 保持顺序；只有规则允许才查看或洗牌；右侧3D牌堆厚度反映数量 |
| 手牌 | 仅拥有者可见内容 | 己方用手牌界面，对手只显示背面/数量；不能进入别人的手牌 |
| 自机区 | 双方可见 | 左侧3D区域，显示计时；只有该玩家选定自机可进入 |
| 战场 | 双方可见 | 单位通常每方6格；道具、结界、时符、乐章不能混算为单位格 |
| 颜色盘 | 双方可见 | 每张牌独立的颜色与横竖状态；不是永久物；默认增长阈值8，并非硬上限 |
| 对抗区 | 双方可见 | 牌和能力按后进先出排列；物理牌与能力对象区分；在桌面内显示待结算项 |
| 墓地 | 双方可见 | 牌归拥有者；保留顺序；右上3D牌堆，查看仍在桌面内铺开 |
| 移除区 | 双方可见 | 规则上双方共用，仍属于游戏内；界面可按拥有者分组显示，不变成两个规则区域 |

副卡组是赛前/盘间套牌配置，不擅自视作第九个对局区域，也不在对局中提供无规则依据的换牌按钮。它目前可保留为组卡功能，具体盘间换备规则另定。

### 6.1 对象身份必须分开保存

- **规则卡牌ID**：一种卡的定义；图像、稀有度、异画另记。
- **实体卡实例ID**：这局游戏中的第几张实体牌，拥有者不随操控权改变。
- **区域对象ID**：每次换区生成新身份（4.05），旧对象上的计时、伤害和每回合次数通常不延续。
- **自机身份**：开局选定的那张实体牌持续保留“所选自机”的资格；不能因生成新区域对象而忘记（1.116a、1.217）。
- **对抗对象ID**：一次使用、启动或触发，包含来源快照、模式、目标引用、X值等；来源离场并不自动使其无效（4.4.3）。

需要保存的状态包括：拥有者、当前控制关系、生效区域、横置/竖置、攻击/阻挡身份、上次取得操控的时点、伤害标记、各类指示物、临时修正、已使用次数与到期条件。普通手牌/墓地牌不拥有横置状态；结界图像横向摆放也不等于横置。

网络和人机获得的是其有权查看的状态投影。隐藏的牌库顺序、对手手牌不能先全部发给客户端再靠界面隐藏。

## 7. 回合状态及推进方式

依据完整规则第5章：

`重置 → 准备 → 抓牌 → 凭依 → 主要〔可多次出牌与战斗〕 → 结束 → 对手重置`

先手首回合按1.24略过抓牌阶段，仍进行凭依。该条比旧教学图“第一回合不抓牌”的概括更具体，裁定确认后固定实现。

| 阶段 | 进入时处理 | 允许玩家做什么 | 退出条件 |
| --- | --- | --- | --- |
| 重置 | 重置主玩家横置的永久物与颜色盘；颜色盘少于8张时将牌库顶正面放入颜色盘 | 无执行权，不能插入出牌；触发先暂存 | 规则动作完成进入准备 |
| 准备 | 放入重置期间及本阶段开始时的触发 | 执行权问询，可使用合法高速牌/能力 | 对抗为空且双方连续让过 |
| 抓牌 | 主玩家抓1张，处理抓牌触发 | 规则动作后问询 | 对抗为空且双方连续让过；先手首回合略过 |
| 凭依 | 可选择一张竖置颜色盘牌与一张手牌交换，也可跳过 | 交换中不可插入响应，之后处理触发并问询 | 完成选择且对抗清空、双方让过 |
| 主要 | 非战斗中开放普通出牌与攻击 | 可反复出牌、起动能力、发起一次次战斗，均须满足时机与约束 | 非战斗、对抗为空且双方连续让过 |
| 结束 | 先处理阶段开始触发及问询 | 处理结束触发、计时、必要弃牌选择 | 完成计时与手牌上限检查、清除到期效果和全场单位伤害，然后换回合 |

颜色盘增长不是抓牌。不能因为牌库顶无法放入颜色盘，就直接套用“抓空输掉”的规则；是否另有相关失败情形按对应规则或后续裁定处理。

### 7.1 执行权与对抗是独立的子系统

引擎要记录：当前回合玩家、当前阶段、战斗子状态、谁持有执行权、连续让过次数、对抗列表、暂存触发、是否正在执行规则动作、是否等待结算内选择。

建议循环：处理规则动作/结算及判定 → 收集待入对抗触发 → 主玩家先排序、另一玩家后排序并入对抗 → 授予执行权 → 合法动作或让过 → 双方连续让过后结算栈顶一项，或推进当前阶段/战斗步骤。

每新增动作或对抗对象，重置连续让过计数。栈顶结算完后重新问询；不能默认对方一直不响应。AI与玩家遵守同一套合法动作列表。

**尚不能写死的点：**1.143b说执行动作后将执行权交给对手，7.1.8a却说使用完成后玩家重新获得执行权。计划先提供统一的执行权授予入口，等裁定后再确定策略，不能直接照搬其他卡牌游戏。

### 7.2 结束阶段需要子状态

建议划分：结束开始触发 → 问询 → 计时清算 → 必要问询 → 弃牌至上限 → 必要问询及再次手牌检查 → 清除直到回合结束效果与所有单位伤害 → 换回合。

按5.6.2a，同一回合因触发返回结束问询后，不能重复减计时。需要保存`本回合计时清算已执行`，并区分“计时只处理一次”和“手牌上限可能反复检查”。触发中断时未完成部分如何续行，列入裁定记录。

### 7.3 结算与判定

完整规则1.22要求即时记录性质变化，但在所有效应处理完毕后进行后续移动或胜负处理；1.22.3还说明判定结果不会改变。因此不能未经确认就实现成普通的“整个效果结束后重算一次”。设计需保留待处理判定记录及依据，尤其测试同一效应内先受致死伤害再回血等情况。具体批次边界待裁定。

结算中要求玩家选择时，仅开放该选择，不把执行权交给该玩家任意出牌。结果返回后从原结算步骤继续。

## 8. 战斗子状态

极彩没有独立的固定战斗阶段（6.0.1）。战斗是主要阶段中可能多次进入的状态，也可能由能力产生。

| 子状态 | 处理 |
| --- | --- |
| 宣言攻击 | 检查可攻击、操控时点、是否竖置、限制；通常横置一个攻击单位，目标通常是对方玩家 |
| 攻击后问询 | 处理攻击触发与双方响应 |
| 宣言阻挡 | 防守方选择0个或多个合法竖置单位，选择阻挡者时横置；检查退治、威吓等限制 |
| 阻挡后问询 | 处理阻挡触发与双方响应 |
| 伤害分配 | 进攻方先选择分配、防守方后选择；分配至合法战斗对象，数值为自然数，合计符合攻击力 |
| 先制伤害（如有） | 仅具先制的单位分配并造成伤害，处理判定，随后问询 |
| 普通伤害 | 存在先制步骤时，仅非先制单位在此分配；没有先制时正常分配；双方伤害同时生效 |
| 伤害后问询 | 处理死亡、歼灭、吸血、追击等相关事件和问询 |
| 战斗结束 | 清除本次战斗身份，回到非战斗主要阶段，再次问询 |

对单位的战斗伤害使用攻击力，对玩家的未受阻挡战斗伤害使用灵力。不能统一扣固定2点。

多阻挡的攻击力可以由攻击方任意分配，允许某个合法对象分到0（6.2.2）；不额外引入“必须先给前一个阻挡者分配致死伤害”的其他游戏规则。

战斗异常必须单独处理：阻挡宣言前失去全部攻击者则终止；已经宣布阻挡后失去所有阻挡者也终止（6.3.2—6.3.3），不能自动改为打脸。未选择任何阻挡者是正常的不阻挡，不是“阻挡者离场”。已经在战斗中时，不执行另一次进入战斗的动作（6.1.3）。

## 9. 支付、约束与能力系统

### 9.1 支付不是一个通用能量整数

记录每张资源牌的可支付颜色、横置状态及支付用途。双色牌每次只能提供自身一种颜色的1点，不是同时提供两点。颜色值能力直接用于支付、不进对抗；不能多支付也不能将一次性产生的多色资源拆剩（1.157、7.1.6b）。自动支付可提出方案，玩家可改选，避免消耗本来想保留的牌。

使用自机单位需要己方操控的永久物颜色覆盖该卡全部颜色；颜色盘本身不满足该约束。角色符卡检查操控的指定角色单位。费用支付与额外约束应一起作为可取消、失败可回退的使用事务。

### 9.2 能力需要描述这些信息

- 归属：主要能力或自机能力；所选自机身份、指示物或神社等持续效果决定自机能力是否获得。
- 种类：基本、触发、启动、静止、替代、规则；静止与替代不伪装成普通出牌对象。
- 生效区域、触发事件、条件、频次、是否可选、谁作选择。
- 模式与目标、费用/额外费用、效果顺序、持续时间与移除条件。
- 需要时记录来源最后已知信息、进入战场选择、X值、支付颜色及模式。

首批效果操作建议：造成伤害、获得/失去生命、抓牌、弃牌、换区、横置/重置、放置/移除指示物、反制、修改属性、获得/失去能力、创造衍生物、检索与洗牌、玩家选择。每个操作都有明确输入与测试，再由卡牌组合。

能力文字用于展示与人工核对，不能成为程序中的字符串关键词判断。不能用“文字里包含火花就扣5血”等方式实现卡牌。

## 10. 3D界面与规则的连接

沿用垫子3作为可配置背景，保留牌库右侧、墓地右上、自机左侧的布局偏好。补齐颜色盘、对抗、移除和战场内的道具/结界/时符显示。除手牌外，牌都作为桌面内对象呈现。

单位格与其他对象区分布局，但都在战场中。颜色盘横置、单位横置、伤害标记、自机计时、时符计时必须清晰可见。50张牌堆厚于30张；显示数量可辅助查看，厚度不代替实际数据。

交互状态与规则状态分开：浏览、选择牌、选择目标、选择模式、选择支付、选择阻挡者、分配伤害、排序触发、选择弃牌、自机返回询问。UI只显示引擎允许的选择和必要拒绝原因，不增加开局强制教程或常驻大段规则解释。

“结束回合”按钮只能提出结束意图，不能跳过对方执行权或未结算对抗。后续可提供按玩家偏好自动让过无可用动作窗口，默认自动化策略应可撤销或设置停点，不代替有意义的选择。

## 11. 建议的代码组织

以下为拟新增结构，当前尚未创建或迁移：

```text
scripts/
  rules/
    match_state.gd         # 对局纯数据及序列化
    rule_engine.gd         # 接受命令，检查合法性，产生事件
    turn_flow.gd           # 六阶段与结束子步骤
    priority_flow.gd       # 执行权、让过与对抗
    combat_flow.gd         # 攻击、阻挡、分配与战斗异常
    payment_rules.gd       # 五色支付、X、混色、颜色值能力
    zone_rules.gd          # 区域移动、对象新身份、自机返回
    effect_resolver.gd     # 常规效果与结算内选择
    judgement_rules.gd    # 判定记录、死亡、胜负
    ability_registry.gd   # 能力与特殊处理器登记
  cards/
    card_loader.gd        # 中文字段读取与规范化
    card_validator.gd     # 格式及能力引用校验
    special/              # 不能用常规组合表达的特殊处理器
  ai/                     # 使用相同合法动作接口的人机
  ui/                     # 菜单、组卡器、对战交互
  presentation/           # 3D对象、动画、桌面布局
cards/                    # 一张规则卡一个JSON定义
rulesets/                 # 规则版本与明确裁定
tests/                    # 规则案例与界面回归
```

数据走向：`玩家/AI/网络命令 → 规则引擎 → 新状态与事件 → 3D/界面显示`。显示层不直接更改血量、抽牌、墓地或执行权。规则模块不依赖3D节点，因此可以无界面测试。

同一局保存规则版本、卡池版本、随机种子、命令顺序及状态摘要。随机洗牌与随机效果由对局统一随机源产生；回放用相同规则和卡池解释事件，不能仅保存一串鼠标坐标。

## 12. 后续开发顺序与验收

不在资料和裁定未确定前承诺“全卡池立即完整支持”。按可验收的小阶段推进，每阶段结束补开发者日志。

| 阶段 | 主要工作 | 完成条件 |
| --- | --- | --- |
| P0 规则与格式定稿 | 用户确认语言；确定规则优先级与关键裁定；定卡牌字段与样例 | 本文决策表有结论；样例卡能由人工读懂、校验器规范明确 |
| P1 规则骨架 | 独立状态、区域身份、命令/事件、对局初始化、4张起手和调度 | 无界面可重放开局，保存原有组卡存档，非法动作不改变状态 |
| P2 回合与资源 | 六阶段、先手例外、颜色盘增长、凭依、五色支付、自机约束 | 可按正式支付进行对局；无固定3能量；失败支付完整回滚 |
| P3 执行权与能力 | 对抗、让过、目标、响应、反制、触发排序、结算内选择、判定 | 两张响应卡按正确顺序结算，每次结算后可再响应；规则动作中不可抢插 |
| P4 战斗与自机 | 多阻挡、伤害分配、先制、持续伤害、自机返回和计时、结束清算 | 完成攻击至战斗结束、回到主要阶段再攻击的全流程 |
| P5 首批正式卡池 | 至少两套合法50张测试卡组所需的已实现卡；关键词与例外 | 每张支持卡有规则案例，不把未实现卡混入正常对局 |
| P6 3D完整交互与人机 | 所有区域、支付/阻挡选择、提示、动画、人机合法动作策略 | 人类与AI完整对局可结束，AI不读取对手隐藏信息 |
| P7 联网 | 权威对局状态、命令校验、版本一致、隐私投影、重连与回放 | 两端同一规则结果，非法/重复/过时命令被拒，隐藏信息不泄漏 |
| P8 扩展和维护 | 更多卡牌、批量导入、人工录入界面、盘间换备与匹配 | 按每批卡/每项功能分别验收，保留历史规则与存档迁移 |

P2中的使用事务和P3中的对抗有依赖：可先在无界面骨架中实现共同接口，不能把“暂时直接生效”的捷径固化。联网开发排在人机基本规则之后，但命令与公开信息边界从P1就建立。

第一批应覆盖：普通单位、自机单位、常规伤害、高速反制、支付道具、持续结界；随后加入时符、乐章及衍生物。现有8张演示卡用作能力实现切片，不能单独承担合法50张卡组验收。

## 13. 需要持续保留的验收案例

| 类别 | 关键案例 |
| --- | --- |
| 构筑 | 50/49/51张；同名第五张；异画同名计数；自机同名混入主副牌；保存草稿容量与开赛合法性分离 |
| 开局 | 双方4张；各自仅一次任意数量调度；换牌随机置底；先手首回合仍凭依 |
| 颜色盘 | 7张会增长、8张不自动增长、效果可超过8张；双色每次只付一点；0费有色；精确支付、失败回退 |
| 自机 | 颜色约束检查永久物；计时不为0不可用；返回是可选替代；换区保留选定自机资格但不保留旧指示物 |
| 执行权 | 双方让过结算顶端一项；执行后新一轮问询；重置与结算中禁止插入普通动作；同时触发排序 |
| 目标 | 单位/玩家范围；全部目标失效不结算；部分目标失效按裁定；同一区域对象离开再回来不是原目标 |
| 战场 | 6个普通单位格；道具/结界不占单位格；满场时单位从对抗与其他区域进入的不同结果；同称号禁止 |
| 战斗 | 单位对单位用攻击、对玩家用灵力；多人阻挡分配；先制两次判定；阻挡者全离场结束战斗；不能嵌套战斗 |
| 结束 | 计时只减一次；弃牌触发后重新检查手牌；清除全部单位伤害与到期效果；手牌默认7张 |
| 胜负 | 生命≤0、需要抓牌时牌库不足、随时投降；牌库空但没有抓牌不能自动判负 |
| 数据/UI | 不改玩家原存档；拖动取消不产生规则动作；动画快慢不改判定；相同种子与命令重放一致 |
| 联网后续 | 对手手牌与牌库不下发；动作执行权/费用由权威端校验；重复命令不重复扣资源 |

每项测试需写出初始局面、动作、预期状态与规则条款。现有演示测试中“抓5张”“固定2伤害”等断言需随正式规则替换；旧测试通过不代表正式规则实现正确。

### 17.1 本次补读范围与结论

2026-09-17补读单位、符卡、道具、衍生物、结界五个牌表，以及FAQ全文。按“有名称记录”提取，共809行（单位380、符卡341、道具32、衍生物26、结界30），按完整名称与能力原文完全一致去重后得到543组。该数字包含异画、标点变化、重印文字差异、错置记录，**不是已确认的独立卡牌数，也不是已实现能力数**。

原先用“常规模板为主，极少数特殊能力再写脚本”描述编牌难度不充分。牌表中大量效果会修改规则查询本身、跨区域生效、改变执行过程或保留历史。应采用可扩展规则引擎，允许卡牌能力直接脚本化；不把所有能力硬塞进越来越庞大的JSON语法。

结论分三层：

1. GDScript作为项目的规则实现语言，没有因已读这些效果而显露出必须改换语言的理由；它仍需要我们实际编写对应机制和测试。
2. 前文的固定“操作+数值”JSON样例只能说明基础效果，不能据此声称覆盖全卡池。JSON保存配置，不会自己解释能力文本。
3. “可扩展实现”不等于“现成支持全部未来用途”。未来新增区域、开局步骤或胜负方式，仍可能需要扩展状态结构、接口、UI和网络协议。不能保证不改引擎就能加入任何新卡。

### 17.3 梦违必须拆成三个独立问题

**第一，是否能进入玩家保存的构筑。**梦违是构筑资格，不是“无法在游戏中使用”。它仍存在于完整卡牌目录中，可以浏览说明，但正常组卡入口、粘贴导入和开赛校验均要执行对应禁入规则。对主副牌等具体槽位采用显式资格配置；本轮用户说明为“不能从常规构筑中加入”。测试模式的放宽不应无意绕过这项限制。

**第二，凭什么在本局中取得这张牌。**给定牌表的「世界ノ间隙·大空魔术」是明确的取得来源：由它的效果开放选择，核对拥有及名称条件，展示后置于手上。不能见到“梦违”标签，就让全部梦违牌自动出现在每一局中，也不能默认取自10张副牌。

需要建立“可供本局合法调用的局外牌池”，其具体范围（玩家拥有的全部目录、预先登记的局外列表或其他范围）尚待规则裁定。该牌池不等于共用移除区，也不是擅自新增的第九个场内区域。联网时只能从双方认可的目录和规则中取得，不能让客户端任意声明新卡。

**第三，取得后的牌如何存在。**创建/引入本局实例，记录规则卡ID、拥有者、取得来源、生成时点和进入区域；后续按明确的身份规则进行使用和换区。“不是从初始卡组带入”不意味着“必定是衍生物”。梦违、衍生物、复制品和普通实体牌的生命周期需要分别定义，不能都套用衍生物离场消失。

### 17.4 未来“开始时加入牌库”的梦违

先区分两个时点：

- **整局对战开始时**：属于开局流程。必须明确在初始洗牌前/后、起手抓牌前/后、调度前/后生效。
- **一次战斗开始时**：属于攻击或效果发起战斗的子流程，一局可能触发多次，不能与开局共用一个模糊事件。

用户提到未来会有此类卡，目前不假定其具体张数、牌名、插入位置或洗牌行为。设计提供上述明确事件，由实际卡文/规则决定绑定哪一个。

假如未来明确规则是“由于已选定的某个来源，初始洗牌前把两张指定梦违牌加入自己的牌库”，则处理过程应为：

`校验玩家提交的50张构筑 → 锁定本局规则与合法开局来源 → 创建初始牌库 → 执行该来源的开局效果、加入2张 → 洗牌 → 抓起手 → 调度 → 第一回合`

此例中的“2张”“初始洗牌前”只是说明架构的假设，不是给当前游戏新增规则。运行时牌库可因此暂为52张，之后抓牌等继续变化。50张只约束提交构筑，不应被写成每次牌库变化后的硬上限。对局结束也不能把这2张自动写回玩家保存的卡组。

开局来源必须可识别，例如选定自机上的能力、已登记的对局规则或合法的开局选择。未在对局中出现的梦违牌不能仅因为数据库里写有“开局能力”就自行触发。开局效果默认不重复执行；重连、读档或重播需要通过事件ID和开局进度避免再次加牌。

### 17.5 修订后的分工

**JSON：记录卡是什么，以及绑定哪些实现。**包括稳定ID、完整名称、称号/角色名、图像、颜色费用、规则属性、构筑资格、能力文字、能力模块ID、参数及版本。对于已有的简单效果，也可继续使用第3节的效果列表。

**GDScript能力模块：描述这张卡如何参与规则。**复杂卡可直接有专属模块，不必先把它翻译成大型JSON程序。模块按能力类型注册到对应入口，共用引擎的支付、选择、查询、换区、伤害和事件系统。

**规则内核：维护一致的执行顺序和不变量。**负责选择恢复、公开信息、对象身份、记录随机结果、执行权、触发队列与回放。能力不能私自改场景节点上的血量或绕过这些服务。

拟议配置片段（仅说明设计，不是已经支持的格式）：

```json
{
  "卡牌ID": "ucs_unit_020",
  "名称": "少女秘封俱乐部「宇佐见莲子」",
  "规则标签": ["梦违"],
  "构筑资格": {"允许常规构筑": false},
  "能力绑定": [
    {"实现": "return_owned_dream_marked_cards", "参数": {"来源区域": "移除区", "去向区域": "手牌"}}
  ]
}
```

此片段只配置莲子的构筑资格和能力绑定；从局外取得它的实现属于「世界ノ间隙·大空魔术」，未来开局加入牌库的实现属于相应开局来源。不要把取得途径全部硬编码进被取得的牌里。

### 17.6 规则内核必须提供的扩展入口

| 入口 | 职责 |
| --- | --- |
| 构筑资格查询 | 是否能入主副卡组、自机槽、同名数量与特殊限制 |
| 开局与战斗事件 | 精确的初始化步骤与每次战斗步骤；开局一次性效果与战斗多次效果分别处理 |
| 合法性/权限查询 | 从哪些区域可使用、目标是否合法、是否能攻击/凭依、谁能看见什么 |
| 使用事务与支付修正 | 费用增减、替代支付、额外费用、X、可选模式与取消回退 |
| 事件发生前的替代/防止 | 改变换区、伤害、指示物等；明确多个修正的顺序，不按节点创建顺序碰运气 |
| 事件后的触发收集 | 可抑制、增倍、延迟触发；保存来源与对象关系 |
| 结算与选择暂停 | 多步骤、双方选择、重复流程、模式与目标，选择完成后恢复原步骤 |
| 持续属性与能力查询 | 复制、改名、能力授予/失去、颜色/数值改变、生效区域与期限 |
| 对抗对象修改 | 重新选目标、复制使用、替换效果；原卡定义保持不变 |
| 回合与胜负修正 | 插入额外回合、立即结束回合、不能输、特殊胜利/失败 |
| 局外取得与实例生命周期 | 合法局外目录、拥有者、来源、换区身份和对局结束处理 |

这些入口需要职责明确的专门接口，不能用一个任意时刻都能改全部状态的通用回调代替。只读合法性查询不允许产生效果；替代和持续效果须确定依赖/顺序，避免递归无限套用。

尤其是「妖精们的居所」：必须保存可组合的能力实例和来源，处理同类复制、重复获得、自引用与失去来源；遇到循环需要规则裁定和稳定的计算方式，不能一遍遍复制文本。能力程序中的选择进度、次数、延迟任务也需要序列化，不能只藏在无法恢复的临时运行栈中。

### 17.7 开发计划调整：先用最难的代表卡验证架构

在P0/P1增加“机制验证”门槛，先不批量制作数百张卡：

1. 梦违构筑禁入 + 大空魔术合法局外取得，验证卡目录、局外来源、实例生命周期分离。
2. 一条明确标为测试假设的开局加入牌库规则，验证运行时牌库增大、存档不变、重连不重复；待真实卡文确定后替换测试假设。
3. 妖精ノ巡礼改写栈中效果，验证对象不等于原始卡定义。
4. 辉夜结束回合 + the world额外回合，验证回合调度和清算。
5. 妖精们的居所动态能力、秦心更换选择人，验证能力组合和可恢复选择。
6. 反魂蝶 + 防止失败/特殊失败，验证胜负不是直接判断血量的单一分支。
7. 八千慧抑制触发与price of life增加触发，验证生成阶段及机制相互作用。

逐项完成独立案例和交互案例后，再确定常规JSON效果库的边界。是否可以批量制作卡牌应以这些原型的验证结果决定，不能只凭一张伤害牌样例宣称引擎通用。

### 17.8 资料清理与新待裁定项

- 同名重印存在标点、拼写及实际效果差异，例如星符「Escape Velocity」有一个或两个防避3的记录。不能按名称自动合并并任选文本。
- 某些行有缺失数值、错置类别或只填了编号。导入时保留原始工作表/行号，并单独标为待核对，不能用0或普通单位等默认值伪造信息。
- 梦违的常规构筑禁入按本轮用户说明记录；局外可选牌范围、拥有的含义、数量上限及获取后的生命周期细节仍需按规则/裁定确定。
- 未来开局梦违的准确时点与授权来源尚未提供；接口预留不等于已经确定卡文。
- 复制、不能响应、多模式次序等旧FAQ与新版完整规则的关系需要纳入原D02、D08、D10和D14的裁定。
